# 前端文案规范

适用范围：`pullcat-web` 的页面标题、按钮、空状态、提示语、状态文案、错误提示

## 目标

Pullcat 的前端文案统一使用任务型表达

任务型文案的判断标准：
- 用户扫一眼就知道当前页面是做什么的
- 用户能立刻判断下一步操作
- 文案不承担营销、鼓动或情绪渲染职责

## 语气

- 直接
- 克制
- 可执行

避免：
- 口号式表达
- 宣传式表达
- 为了“有设计感”而加的包装文案

示例：
- 用 `审查历史`，不用 `过往结果一站回看`
- 用 `登录 GitHub`，不用 `连接 GitHub，再继续审查`
- 用 `对比结果`，不用 `两次审查，差异一眼看清`

## 标题规范

页面标题只回答一个问题：`这里能做什么`

- 首页：`开始审查`
- 登录页：`登录 GitHub`
- 历史页：`审查历史`
- 对比页：`对比结果`
- 仓库页：直接使用仓库名，必要时补任务性副标题
- 设置页：没有必要时可以不放页头
- 仓库规则页：直接使用仓库名或 `规则设置`

禁止重复使用以下包装型栏目头：
- `当前关注点`
- `工作台摘要`
- 类似“先把……配好”“一眼看清”“这里只负责……”的解释性口号

## 按钮规范

按钮统一使用 `动词 + 对象` 或稳定短动词

推荐：
- `开始审查`
- `开始对比`
- `取消对比`
- `添加规则`
- `添加仓库`
- `管理 Webhook`
- `登录 GitHub`
- `删除`

避免：
- `去登录`
- `一键添加 3 条`
- `前往审查历史`

替代建议：
- `登录 GitHub`
- `添加全部建议`
- `查看审查历史`

## 空状态规范

空状态使用两段式：
- 第一行说明当前为空
- 第二行或按钮给出下一步

示例：
- `暂无审查记录`
- `还没有自动发布仓库`
- `暂无自定义规则`

不要写成长段说明，也不要借空状态做产品介绍

## 状态与反馈规范

状态标签优先短词：
- `已连接`
- `未连接`
- `已启用`
- `已禁用`
- `分析中`
- `失败`

Toast 和反馈文案遵循：
- 成功：简短确认，例如 `规则已保存`
- 失败：明确动作，例如 `保存规则失败`
- 网络或服务异常：说明动作 + 建议排查方向

## 术语统一

全站固定使用以下术语：

- `审查`
  不混用 `Review`
- `审查历史`
  不混用 `历史记录` 作为页面主标题
- `规则`
  不混用 `建议规则`、`检查项`
- `自动发布`
  不混用 `自动回写` 作为主名称，`回写评论` 只作为补充说明
- `登录 GitHub`
  不混用 `去登录`、`连接 GitHub`
- `对比结果`
  不混用 `差异一眼看清` 等修辞标题

## 副文案使用规则

只有在以下情况才添加副文案：
- 用户不知道输入格式
- 用户不知道动作后果
- 用户不知道下一步

如果标题、字段名、按钮文案已经足够清楚，就不要再补一句重复解释

示例：
- 保留：`输入 owner/repo`
- 保留：`开启后，新审查完成时会自动发布结果`
- 删除：`这里只负责看变化`
- 删除：`先确认 GitHub 连接正常，再为需要的仓库补上...`

## 落地检查清单

提交前检查：
- 页面是否还存在宣传型标题
- 同一动作是否出现多个说法
- 按钮是否可以脱离上下文独立理解
- 空状态是否给出明确下一步
- 副文案是否只在必要时存在
